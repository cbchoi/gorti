## Changes

### Available GALT And Grant Safety

Previously GALT used other regulators' last granted times plus lookahead,
ignoring their committed pending requests. A peer pending TAR(10) with
lookahead 2 could therefore still contribute 2 instead of 12.

The time service now calculates the available peer bound under its evaluator
lease and state locks. The GALT RPC, LITS and MOM observations use that common
calculation. It excludes the querying regulator directly, uses projected actual
lookahead, considers queued messages that can cause early NMR/NMRA grants, and
propagates possible FQR early-grant bounds. Retraction removes a queued
early-grant constraint; rejected delivery admission does not remove it.
No other regulator means undefined GALT. Queued incoming messages can still
define LITS when GALT is undefined.

In the current finite float64 representation, an exclusive zero-lookahead
boundary uses the next representable value as the first permitted send time.
This is not the standardized interval epsilon and does not complete W2.

Review exposed a related grant-loop defect, not just a query discrepancy.
With three regulators, an early NMR peer could grant at 4 and subsequently send
at 5, yet a TAR/TARA requester with a smaller handle was granted to 9 first.
Changing the requester's handle reversed the outcome. The new four-case
regression initially failed both smaller-handle cases and passed both larger-
handle controls.

Each constrained candidate now uses the smaller of the configured strategy's
bound and its available peer bound. State locks are released before the
strategy or outbox is called; the evaluator lease covers the decision and
admission. The loop recalculates after each grant. The four cases now pass,
along with repeated tests for third-party arrivals, chained pending requests,
retraction, failed grants and concurrent outgoing admission.

### Strict Range Admission

Set Range Bounds now rejects equality as well as inverted or oversized bounds,
before assigning pending state. Domain and real RPC tests check zero, interior
and upper-limit equality, finite FOM limits, uint64 endpoints, omitted wire
bounds and preservation of previously pending values. Valid nonempty ranges
still commit normally.

Both Python interfaces reach DDMService.SetRangeBounds and report the exact
`InvalidRangeBound` exception and wire trailer. SupportService has dimension
queries, not a second range-setting RPC. Live tests check consistent dimension
handles and limits across the two services.

The overlap rule and snapshot reader are unchanged. A dedicated compatibility
test restores old committed and pending equal-bound ranges, verifies round-trip
state, and then rejects a new zero-width setter call. Reading a legacy snapshot
does not make that new call valid under 10.30.3(i).

The Python evidence configuration contained duplicate keys, which the ordinary
JSON loader silently overwrote. The shared reader now rejects duplicates in any
configuration object. Three tests reproduce identical file keys, conflicting
categories and duplicate selection flags before the fix. Existing entries were
deduplicated without removing any selected case. This is an engineering guard,
not an additional IEEE requirement.

Stale time-service comments describing incremental TAR grants and incorrect
clause numbers were corrected. There are no Protobuf field/RPC changes, new
configuration options or SDK production changes in this batch.

The first full Python run also exposed a test-fixture threading error: the M39
fixture injected callbacks directly into an asyncio queue owned by the
ambassador's other thread. Two tests missed discovery callbacks, although they
passed in isolation. A deterministic regression reproduced injection without a
running event loop. The fixture now schedules injection on the owning loop;
payload/type assertions and the existing timeout are unchanged. This fixes
test execution, not the production network callback implementation.

## Receive-Order Follow-Up

Source review confirms that a constrained, time-granted federate with
asynchronous delivery disabled is not eligible for RO messages. Nonconstrained
federates may receive them in either time state; asynchronous delivery permits
RO delivery while constrained and time-granted. Control callbacks are not
automatically subject to these message-delivery rules.

The current object service bypasses the TSO admission gate for untimestamped
messages. The time manager has a TSO queue but no separate pending RO queue;
changing the asynchronous flag alone cannot implement the required behavior.
This remains an implementation gap, not a passing result of this batch.

The next RO change must cover these linked boundaries together:

1. Classify reflection, interaction and removal messages independently of
   control callbacks. Retain timestamps on messages delivered in receive order.
2. Admit an entire recipient set atomically, queue ineligible RO messages and
   reevaluate eligibility when an advance is recorded, asynchronous delivery is
   enabled or time constraint is disabled.
3. Deliver the required queued RO messages before the grant, preserving a
   retryable queue and withholding the grant when admission fails.
4. Persist pending RO state with an explicit version, restore/rebind typed
   identities, and clear it on resign or federation-generation teardown.
5. Reevaluate current subscriptions at delivery, retain scheduled-save
   boundaries and distinguish pending-message counts from transport envelopes.
6. Verify constrained/regulating/async combinations, idle and pending states,
   mixed RO/TSO callbacks, failures and restart through the Python binding.

Same-current-time TSO eligibility, unengaged advance requests and delayed
subscription evaluation also require source-derived checks. The current
float64 representation and complete standard binding remain separate work.
