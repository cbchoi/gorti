# Python support lookup and rejoin fixes

Date: 2026-10-01. This increment repairs the two defects reproduced during
the [requirements traceability review](ieee1516-2010-traceability-20261001.md).
It preserves the prior failing records and the historical server executable.

## Changes

The public Python `getObjectClassHandle` now raises `NameNotFound` for an
absent class name. The server supplies `rti-spec-exception=NameNotFound`, and
the SDK exports the exception from both `rti1516e.errors` and `rti1516e`.
For older servers without that trailer, only this by-name operation uses a
narrow fallback based on the returned status and detail. Recognized exception
metadata takes precedence. By-handle and synchronization mappings are unchanged.

After a successful resign, the transport marks the federation generation
cache stale. The next generation-dependent lifecycle operation confirms the
current generation through `ListFederations`; repeated use after confirmation
uses the cache. A failed catalog lookup does not fall back to the stale value.
A failed resign does not invalidate the active generation fence.

If the name now identifies a different execution, the old logical-time and MIM
defaults are discarded before constructing the join request. If the execution
is unchanged, those confirmed defaults remain. The request still carries its
expected generation: there is no blind join retry and no weakening of server
generation validation. Recreation between catalog lookup and join remains
subject to that validation.

The server wire change is limited to error metadata; no Protobuf field or RPC
signature is changed. The SDK fix also works with the historical server.

Before the fix, the two actual-server reproductions failed. The focused Python
unit set then produced four expected failures and four passing controls;
the new Go gRPC test failed because the exception trailer was absent.

skipped behavioral test. There were no failing or skipped behavioral Go cases.

The live scenarios cover the two repaired failures and the four prior contracts:
duplicate creation, destruction with joined members, deletion errors with
continued object usability, and persistence of contributed FOM definitions.

after remote recreation, and successful unchanged-execution/fresh-connection
controls. All 12 updated-server processes were closed; the executable hash was
unchanged before and after execution.

Unit tests additionally cover failed resign, unavailable or absent catalog
entries, unchanged versus changed generations, and a recreated execution that
selects Integer64 time without inheriting the old execution's MIM.

## Assessment

The two reported defects are repaired within the tested scope. The lookup
expectation is linked to IEEE 1516.1-2010 service 10.6 and the supplied standard
Java API; these executions exercise the product Python binding, not Java API
conformance. The rejoin cache behavior is an engineering lifecycle requirement,
not a claimed IEEE-prescribed caching algorithm.

These are internal black-box checks, not organizationally independent
certification. The locally built executable is identified by its hash, not a
signed source-to-binary attestation. Full-family requirements inventory,
standard-Java API verification, and remaining conditional obligations remain
separate work; this increment does not assert full IEEE conformance.
