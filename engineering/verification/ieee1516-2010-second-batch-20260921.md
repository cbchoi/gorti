## Method And Sources

Parallel work covered time boundaries, ownership, DDM, Python live behavior,
concurrency review and Linux verification. Each implementation loop used plan,
do, review and reflect: reproduce the discrepancy, correct the owning service,
review failure/persistence paths, then run focused and broad regressions.
Independent work streams are not independent standards certification.

The active 2010 text of the supplied IEEE 1516.1 redline is the source for the
semantic corrections. Deleted text was excluded. The source identities are in

## Changes

### Zero-Lookahead Boundaries

Source: 8.1.4, 8.1.6 Table 3 and 8.2; supplied PDF pp. 184-188 and 192.

- Finite zero-lookahead TAR/NMR requests exclude equality at the pending target
  and resulting granted time. Available requests retain inclusive bounds unless
  an earlier strict grant at the same time still excludes equality.
- A same-time Available grant does not erase strict grant history. Forward
  advancement replaces that history, and enabling regulation resets it.
- Positive-lookahead bounds remain inclusive. Pending bounds use projected
  actual lookahead, including a reduction in progress.
- The grant evaluator and outgoing validator share one boundary calculation.
  The existing float64 strategy port represents an exclusive finite bound by the
  next representable value. This is not the constant interval epsilon of 12.3
  and does not implement exact integer logical time.
- Failed grant admission restores the previous strict history as well as the
  time state, for reserved and legacy outboxes.

Time snapshots write version 3 when strict history exists, version 2 for a
pending decrease without that history, and version 1 otherwise. The reader,
restore graph and federate rebinding accept all three. Tests reject a strict
history field in older versions, malformed state and unsupported future versions.
Version 1/2 snapshots cannot recover completed grant history they never stored;
pending request modes still determine their pending bound. Older readers must
reject version 3 instead of silently dropping history.

The product's positive-infinity sentinel retains its previous behavior. The
source-derived strict-bound claim here is limited to finite float64 values.

### Atomic Outgoing Admission

The reproduced race was between optimistic timestamp validation and final
delivery admission: a grant or lookahead change could invalidate the timestamp
in between. Final sender validation now retains the federation evaluator lease
through queue/outbox admission. Advance-request recording, lookahead changes,
regulation changes and federate time-state removal use that same boundary.
Observers and follow-up grant evaluation run after lease release.

This applies to interaction, attribute update and deletion paths, including
wire-keyed variants, scoped interactions, receive-order downgrade and empty
fanout. A rejected send produces no journal/callback/queue effect and does not
consume its retraction identity. Tests verify a valid retry with the same ID.
Delivery of an already accepted deferred deletion uses delivery classification,
not a new validation against the sender's later time.

The 60-case object/time matrix passed 20 repetitions. Direct lease tests cover
commit/release, empty/buffered reservations, invalid validation and observer
reentry. This is concurrency engineering evidence, not an additional IEEE
requirement. Destructive federation lifecycle still relies on the production
membership/generation admission boundary to quiesce service calls.

### DDM

Source: 9.1.3.2(b), 9.1.4 and 9.9; supplied PDF pp. 224-225 and 240.

An empty object-region unsubscribe collection now leaves subscriptions
unchanged after validating the request. Range overlap includes equal lower
bounds as specified, with routing and restore coverage. The existing unit and
M10 tests that treated this equal-lower case as disjoint were corrected from
the source, not merely changed to match the implementation.

The separate lower-less-than-upper admission rule for Set Range Bounds
(10.30.3(i), PDF p. 272) remains open. Predicate tests using seeded zero-width
state do not establish that such a range is valid to create.

### Ownership Confirmation

Source: 7.6.3(g-h), 7.6.5(a-b); supplied PDF pp. 165-166.

Confirm Divestiture now distinguishes a confirmation never requested from a
previously requested confirmation whose willing acquirers withdrew. The latter
returns the affected attributes to waiting for acquisition without transferring
ownership; a later acquisition can request confirmation again. Mixed attribute
sets retain unaffected state. Checkpoint state and callbacks are covered.

Late integration review found that the persistence adapter discarded the new
confirmation-request flag even though the domain snapshot retained it. A
regression reproduced both lost confirmability and the wrong exception after a
withdrawn acquisition. A versioned ownership extension now retains that flag for
every pending divestiture, with restore-graph validation and federate rebinding.
It follows the existing MOM envelope pattern without changing Protobuf fields.
Old protobuf-only snapshots remain readable; their two-phase offer/acquirer
combination retains legacy confirmability, but previously unstored withdrawn
history or custom-strategy decisions cannot be reconstructed. Malformed/future
extensions fail before state mutation, and old readers reject new extensions.

The existing gRPC exception metadata and Python translation preserve
`AttributeDivestitureWasNotRequested` and `NoAcquisitionPending` distinctly.
An ambiguous legacy transfer-state error remains ambiguous. No Protobuf/RPC
descriptor change is part of this batch.

  schema-oracle skips require a corrected full rerun, not a passing verdict.
