# Java Declaration, Object And Synchronization Increment

Date: 2026-09-22

## Result

The Java provider now maps 103 of the 172 standard `RTIambassador` signatures,
up from 45 in the foundation increment. The remaining 69 signatures fail
explicitly. This inventory counts forwarded signatures, not proven normative
requirements or a conformance percentage.

On Windows with Temurin 11.0.31 and Maven 3.9.16, the complete Java test run
passed **136 tests, zero failures, zero errors and zero skips**. Six cases used
a real local Go RTI; the other 130 were unit or in-process transport cases.
The public example also completed with two independent Java processes.

No Go/Python/C++ implementation, Protobuf schema or RTI algorithm was changed by
this increment. The current Go server was rebuilt for the live tests. This is
functional evidence, not a performance measurement or whole-RTI verdict.

## Implemented Scope

| Area | Addition |
|---|---|
| Collections | Seven standard collection factories; mutable sets, value maps and attribute/region pair lists; clone, serialization and byte-wrapper behavior |
| Declaration | Object attribute and interaction publication, unpublication, active/passive subscription and unsubscription |
| Object services | Single/multiple name reservation and release; registration; RO and timestamped updates, interactions and deletion; local deletion; object/class update requests; retraction |
| Support | Class, attribute, interaction, parameter and federate lookups; callback-visible object lookup; order and transportation names |
| Synchronization | Registration for all current members or an explicit nonempty set; success/failure, announcement, achievement and failed-participant set |
| Callbacks | All nine reflect/receive/remove overloads; discovery producer, tags, bytes, sent/received order, transportation, regions, retraction identity, update requests and advisories |

`AmbassadorServices` retains membership and callback lifecycle.
`ExchangeServices` handles declaration/object/support requests;
`SynchronizationServices` tracks announcements and achievement.
`ExchangeCallbacks` converts wire events into the standard callback forms, and
`ExchangeKnowledge` maintains only locally visible object state. A narrow
`ServiceContext` shares connection and federation identity between these
adapters. The generated facade forwards to typed methods with each standard
signature's declared checked exceptions.

## Plan, Do, Review, Reflect

### Plan

Select the next runnable Java federation slice without altering server services
or the standard API declarations. Split collection types, exchange adapters,
independent live tests and the two-process example into separate work areas.
Use the supplied IEEE 1516.1-2010 redline's clauses 12.8-12.10 for overload
selection and the existing source-reviewed Python deletion/retraction cases as
cross-checks for local object knowledge. Source PDFs remain outside Git.

### Do

First compile and run the new live exchange test against the previously built
foundation provider. The test reached the real RTI and failed at
`getObjectClassHandle` with the expected not-yet-implemented error. This was a
behavioral RED result, not a missing dependency or compilation failure.

Implement service adapters, typed collections and callback conversion. The
first integrated GREEN run passed 118 tests, including real exchange and the
existing FM/TM live case.

### Review

Independent review and integration checks identified these defects before
acceptance:

| Defect | Correction and regression evidence |
|---|---|
| Retraction triples could collide across federation names | Include federation name as well as generation, producer and message ID; reject foreign-federation handles |
| FQR-delivered deletion hid an object before its deletion time | Keep provisional TSO removals visible until the matching time grant or constraint disable; live FQR(10), delete(5), TAG(1) regression |
| Timestamped-RO deletion could not restore object knowledge | Preserve restoration state and restore before `requestRetraction`; live lookup and subsequent real update |
| Native messages without retraction tracking were rejected | Deliver the received-TSO overload with a unique local non-retractable identity; tests cover absent and zero wire IDs for reflect/receive/remove |
| Decoder failure committed removal without invoking the callback | Commit only after complete decoding and actual invocation; retain the commit when the user's callback itself throws |
| Empty targeted attribute sets could become whole-class operations | Reject the unrepresentable call before RPC instead of broadening its effect |
| Issued retraction IDs accumulated for every timestamped send | Constant-space unsigned allocation bounds; backend remains authoritative for failed-send gaps and expired/retracted messages |

The exchange adapter's focused review tests progressed from 14 to 24 cases.
Four live deletion/retraction cases and additional callback/handle regressions
were added before the final full test run.

### Reflect

Payload equality alone did not detect the important defects. The final cases
also inspect callback overload, local lookup before/after delivery, grant time,
producer identity, typed failures and use of restored objects. A positive
two-federate exchange remains insufficient to close the complete Java mapping.

The live JUnit cases use separate RTI sessions within one JVM. They check real
server enable callbacks, peer-blocked time advance, all five advance requests,
RO/TSO exchange, metadata, failed synchronization participants, object lookup
lifetime, retraction restoration and cleanup. They do not use an in-process
fake RTI as their server.

Separately, `examples/java-exchange/run.ps1` launched a publisher and receiver
in distinct processes against a fresh local server. Both verified the `ready`
and `done` barriers and exited zero. The receiver verified exact update and
interaction bytes/tags, reliable RO delivery and the producer handle. The
publisher destroyed the federation after both resigned. Launchers do not build
concurrently or depend on test classes.

The facade/inventory generator's `--check` passed. PowerShell and Bash launchers
were syntax-checked; the actual two-process execution was Windows-only. Linux
Java runtime execution and cross-language Java/Go/Python campaigns are still
pending. No current Go/Python regression count is inferred from these Java tests.

## Reproduce

From the repository root, start a local server:

```sh
go run ./rti/cmd/rtid --listen=127.0.0.1:50051 --metrics-listen=127.0.0.1:0 --admin-listen= --log-level=warn
```

Then run the Java tests with a real endpoint:

```sh
mvn -f javasdk/pom.xml "-Dgorti.endpoint=grpc://127.0.0.1:50051" "-Dgorti.fom=/absolute/path/to/gorti/examples/go-tar-wait/tar-wait-fom.xml" verify
```

Without the endpoint property, live tests are explicitly skipped; that run
must not be reported as the 136-case no-skip campaign above. Exchange and
retraction tests use their bundled exchange FOM; the explicit FOM property is
for the foundation live test. Use the
[example instructions](../../examples/java-exchange/README.md) for independent
JVM execution.
