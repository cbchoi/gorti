### FDD Compatibility

The existing DDM registration fixture contains the legacy dimension value `NA`.
Initial validation rejected it, exposing a compatibility regression in the full
suite. The parser and MIM decoder now retain it without changing the fixture.
The official-XSD vocabulary does not accept this literal, so standard FDD export
returns an explicit unsupported error rather than replacing it with another
value or emitting schema-invalid XML. Empty and otherwise invalid values remain
rejected. This is an input-compatibility policy, not a new standard vocabulary.

Independent XML vectors check current-FDD contents before and after additive
join, aborted candidate changes, committed changes, JSON snapshot and restore.
Savebundle tests restore into a fresh repository after removing the source
repository and distinguish prepared, aborted and committed restoration. Failed
conflicting joins leave published FDD and saved state unchanged.

### Caller Identity And Locking

The session token identifies a candidate membership; it does not authorize an
old numeric handle. The resolver holds the relevant lifecycle leases, checks
generation and incarnation, and authenticates the currently bound handle.
Observation leases remain held until MOM reporting completes.

An actual signed checkpoint query reproduced a recursive admission-lock wait.
The membership interceptor now exposes its held admission through request
context, and the resolver reuses that lease. Requests crossing federation
identities are not assigned speculative MOM attribution. Ordinary nonzero-handle
object/send requests do not allocate this additional context marker.

Review identified a remaining scaling concern: handleless token lookup scans
sessions, and membership resolution copies/sorts a roster. No scaling benefit
is claimed. A future indexed identity lookup must retain the same lifecycle
fencing and be measured before replacing this path.

## Experimental Foundations

### R3 Delivery Accounting

The standalone ledger is under `rti/experiments/algorithms/deliveryledger`.
It records observed admissions, moves and terminal outcomes per membership and
callback epoch, with a bounded live set and explicit lost-coverage state.
It has no production callers and does not populate `HLAROlength` or
`HLATSOlength`. Its observed counters are not independently measured queue totals.

Keeping it in the runtime delivery package created a test import cycle through
object-event classification. Moving the unintegrated prototype into experiments
removed that dependency without modifying the production outbox or weakening
object tests. Independent review also reproduced a retired-transfer validation
defect; its correction and regression results are included in the final tests.

Production completion still requires a shared transfer identity through time
queues, outbox, transport and SDK callback queues; observable SDK enqueue and
terminal events; retry/cancellation semantics; and reconnect/restore conservation.
A successful stream send or producer ACK does not prove callback invocation.

### R5 Strict C++ Foundation

A separate C++14 foundation compiles the shared exception, variable-data,
callback-base and float64-time code against unmodified official headers.
Factory allocation failures are translated to the declared exception contract.
Modern C++17 headers and their ABI were not changed by this increment; the
modern preprocessed logical-time implementation remained equivalent.

The strict and modern libraries must not be linked together in one executable:
their public namespaces overlap while ownership types and virtual layouts
differ. The strict foundation is not a complete strict RTI service library.
The service frontend still needs a C++14-compatible boundary to the C++17 backend,
matching override exception contracts, and complete callback/service coverage.
Integer64 time remains unimplemented in this work order.

## Direct Measurement

An initial retained-FDD microbenchmark compared the pre-batch source and the
metadata-retention increment with identical FOM bytes, compiler and benchmark
code. It used `GOMAXPROCS=1`, five warm-up pairs, 30 measured pairs, alternating
AB/BA order and 100 ms per Go benchmark. The companion benchmark was added to
both inputs; baseline product sources were not changed.

| Operation | Baseline mean | Initial increment mean | Paired geometric time ratio, 95% CI | Bytes/op, before to after |
|---|---:|---:|---:|---:|
| Parse | 510.3 us | 551.2 us | 1.0765 [1.0222, 1.1336] | 401,604 to 465,235 |
| Export | 96.17 us | 100.87 us | 1.0317 [0.9921, 1.0730] | 70,698 to 71,114 |

The interval uses the mean paired log ratio and a t interval with 29 degrees of
freedom. The parse estimate is slower and allocates more memory. Wider retained
records and defensive copies are plausible contributors, not isolated causal
proof. This was a shared development host, and later compatibility corrections
were not in the measured binary. These are diagnostic initial-increment results,
not final-release performance, message/TAR latency or a comparison with Portico.
No new full DEVStone-HLA performance claim is made.
