## Traceability Records

The [atomic obligation inventory](ieee1516-2010-normative-obligations.json)
records 20 source-reviewed requirements across the three supplied publications.
Each row contains the source hash, clause and one-based PDF page, responsible
subject, applicability, conditions, implementation paths, literal test names
and outstanding evidence. Twelve rows have implementation and test links;
four have newly executed passing internal black-box evidence. All 20 retain open
assessment items. These are seed rows, not a census or a conformance percentage.

RTI obligations are separated from federation-model, federate-state, SOM and
OMT-tool responsibilities. A server test cannot establish the completeness of
a user's SOM or the correctness of its simulation model. Full Java mapping
and callback coverage also cannot be inferred from the product Python API.

The [traceability checker](../../scripts/ieee2010_traceability.py) performs
three different checks:

- Normative source identity and clause/page records. Source hashes are checked
  against the private supplied PDFs; the tool does not interpret their text.
- Implementation and test links. Python uses its AST; Go and Java use bounded
  lexical declaration checks that reject comments, literals and mere calls.
  Link validity is not compilation, collection, execution or oracle correctness.
- Executed records. Go transcripts are checked again for exact manifest,
  command, package and run/pass lifecycles. Python records bind the binary,
  test source, selected command, JUnit artifact and individual case/module names.
  Failures, skips, missing cases, contradictory totals and stale hashes reject
  the imported campaign.

`RECORDS_VALID` means those record checks passed, not that an IEEE obligation
is closed. The checker never executes tests, modifies the existing quality
gate, or awards conformance. Explicitly imported records are trusted local
inputs, not authenticated attestations.

## Independently Specified Behavior

The [public-client tests](../../pysdk/tests/test_ieee2010_independent_contract_live.py)
derive expectations from retained/added 2010 text and rendered source pages,
not from Go handlers or internal snapshots. FOM inputs and callback observers
are separately authored. Tests use real public connections, exact exception
types, observable post-state and successful controls, without mocks or xfails.

| Requirement | Source locator | Asserted behavior |
|---|---|---|
| `IND-FM-DUPLICATE` | 1516.1 4.5.3(b), 4.5.5(g), PDF 53 | Duplicate creation rejects; the original class remains usable; recreation succeeds with a fresh connection |
| `IND-FM-DESTROY-JOINED` | 1516.1 4.6.3(c), 4.6.5(a), PDF 54 | Destruction rejects while members remain, preserves usable membership, then succeeds after resignation |
| `IND-OM-DELETE-UNKNOWN` | 1516.1 6.14.3(e), 6.14.5(c), PDF 132 | A real but undiscovered object rejects deletion as unknown; a known nonowner rejects for privilege; update and owner removal remain correct |
| `IND-FOM-CONTRIBUTOR-PERSISTENCE` | 1516.1 4.1.4.1, PDF 49 | Accepted additional class/attribute definitions remain usable after every member resigns, through a fresh public connection |

No universal exception precedence, full FDD-content equality, contribution
absence after recreation or same-connection rejoin guarantee is inferred from
these four passing scenarios.

Independence here means separately authored oracles and black-box observation
within the same project. The tests still use gorti's Python SDK and protocol.
They are not organizationally independent assessment, cross-vendor comparison,
standard-Java verification or certification.

## Retained Failures

The initial four-scenario runs exposed additional support/lifecycle problems
outside the final passing expectations: an absent-class lookup produced
`SyncPointNotFound`, and reuse of a resigned connection after destroying and
recreating the federation name produced a generation-mismatch join error.
An attempted public `HLAcurrentFDD` query did not provide that value on the
pinned executable; its required query/subscription conditions need separate
review before classifying it as a normative defect.

The [separate gap reproducers](../../pysdk/tests/test_ieee2010_independent_support_gaps_live.py)
then reproduced both support/lifecycle problems twice: two ordinary failing
tests in each run, with no skips/errors. The lookup expectation was checked
against 1516.1 service 10.6 (PDF 252) and its incorporated Java API: the correct
by-name exception is `NameNotFound`, not the exploratory `ObjectClassNotFound`.
Python instead returned `SyncPointNotFound`, while valid lookups before/after
the rejection succeeded. This is a product error-category/mapping gap, not
proof that the standard Java binding fails.

The rejoin reproducer includes successful same-connection rejoin into the
unchanged execution and successful fresh-connection join into the recreated
execution. Only the still-connected old member fails after another connection
recreates the name. It remains an engineering SDK lifecycle gap; no IEEE
requirement for gorti's generation-cache algorithm is invented. All four
additional owned servers closed. Production fixes were not made in this
verification increment.

Earlier failed runs remain preserved. The final controls use actual class
usability and fresh connections; they do not catch those errors as successes
or claim them fixed. The seven development runs contain 25 test executions:
20 passed and five failed, with no errors/skips. Only runs 06 and 07 bind the
final four-test source. All 25 owned server processes closed, including the
failure paths. Termination status is distinct from the pytest verdict.
